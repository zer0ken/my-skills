# Session cleanup

Execute cleanup when invoked. A session runs this skill itself when its assigned work is finished, meaning what the work was for has ended, such as its PR merged, its issue closed, or its deliverable handed over with nothing left, and it runs it before the final report so the report carries the result; it does not end with a suggestion to run it or a question whether to. Workflow finishing requires execution too. Address the user in Korean using the neutral technical written-style rule.

## Ownership and preservation

Inventory resources created or allocated by this session from its actual records: temporary files, worktrees, processes, containers, Docker images, Paseo registrations, Orca workspaces, workers, terminals, and automations, and other allocations. Confirm the execution host and any container or SSH boundary. An unfamiliar name or location is not proof of ownership. Include only resources used exclusively by this session; leave shared resources, other sessions' changes or worktrees, user deliverables, reused images, and servers intact. Report uncertain ownership and retained resources with reasons. Never start, stop, restart, or replace a model server without the user's permission for that action.

Decide which data has a concrete reuse purpose before deleting anything. Preserve useful data under `~/agent-assets/<project>/<asset>/`, outside the project. Derive project and asset names from confirmed identity; avoid secrets and personal data without an authorized reuse purpose. Contents have no required format except a lowercase `readme.md` explaining origin, purpose, reuse instructions, and required files. Use a new run or asset name when a destination already contains different data. Do not archive ordinary temporary files merely because they exist.

Verify the preserved files and `readme.md` before removing their source. Record the discoverable absolute path, summary, date, original user request or decision, and validity condition in the executing agent's existing memory mechanism. This is reusable work context, not a new global instruction; do not copy it into every agent's memory. If preservation or memory recording fails, retain the source and report the failure.

Each round directory of finding-response records under `~/.agents/responses/<session>/`, as the `response-rv` skill defines them, is preserved under `~/agent-assets/<project>/finding-responses-<session>/` when it holds context that outlives the session and that the artifacts, commits, PR, or issue do not already carry, and deleted otherwise; records kept inside a run directory stay with that run.

## Context notes

Context notes, as `~/.agents/skills/take-a-note/SKILL.md` defines them and the instructions' `Context notes` rule requires, are decided and then organized, never only deleted. The targets are every note in the vault `~/notes` whose `session` property is this session's id (`grep -rlx 'session: <id>' ~/notes`). The user's words (2026-11-24), given as a general instruction on cleanup: "take-a-note로 생성한 노트 중, "사용자의 명시적 설계 결정"이 포함된 노트는 절대 클린업으로 제거하지 마. 그리고 클린업에서 단순 제거가 아니라 작성된 노트들을 나중에 찾기 쉽게 정리하는 작업을 해".

1. Read each target note in full and decide it. A note that holds a user design decision, as take-a-note defines it, is kept, whether or not it carries the tag `user-decision` and even when a PR, issue, or commit also records the decision; a note whose content leaves it in doubt is kept too. Any other note is kept when it holds context that outlives the session and that the artifacts, commits, PR, or issue do not already carry, such as an open decision, work left for a follow-up, or a finding about the codebase, and deleted otherwise. A kept note stays in the vault, which is already outside every project. Before deleting a note, check with `grep -rl '\[\[<note name>\]\]' ~/notes` that no kept note links it, and keep it if one does.
2. Organize every kept note. Add `user-decision` to the `tags` of a note that holds a user design decision and lacks it. Move a note that sits outside the `~/notes/<project>/<work>/` directory take-a-note's location rules give it into that directory; its vault-unique name keeps every `[[<note name>]]` link to it working. Fill the properties take-a-note requires that the note lacks, from its own content and the session's records.
3. Update the work index `index-<project>-<work>.md` of each work directory that holds a target note, creating it when it is missing, in the form take-a-note's location rules give. Add a line for each kept target note under `## 사용자 설계 결정` or `## 노트`, remove the line of each deleted one, leave the lines of other sessions' notes as they are, and rewrite `## 작업` to the work's current state. A line already present for the same note is updated, not duplicated, so a repeated cleanup leaves the same index.

List every note in the report with its decision, its move or property change if any, and the reason in one line, and name each work index written.

## Worktrees

Every worktree the session created is a cleanup target, and the session finds them from the records the `worktree` skill wrote, not from what it remembers: run `python3 -I ~/.agents/skills/worktree/bin/worktree.py list` and take every line it prints, then follow the Remove section of `~/.agents/skills/worktree/SKILL.md` for each: preserve uncommitted changes as a commit or diff and needed ignored files by copying, then `worktree.py remove <path>`, which keeps the branch and drops the worktree's Serena registration. Keep a worktree only when the work it belongs to has not ended, such as a PR still in review, and report it with that reason. Run `list` again after removing, and report every line of the first `list` as removed or retained with its reason. Add the worktrees the session's own commands or context notes show it created without a record, and handle them the same way. The user's words (2026-11-19): "그 세션이 클린업할때 워크트리 정리하는거 까먹지 않게 해".

## Paseo registrations

A Paseo project, with the workspaces under it, that Paseo registered for a directory this session or a worker it launched created, such as a measurement or temporary worktree or a temp directory, is a resource of this session even though the session never ran `paseo project create`: Paseo opens a project for a directory no workspace owns ("Without `--workspace`, creation opens the project at `--cwd` or the current directory and reuses its oldest active workspace", https://paseo.sh/docs/cli), and that registration stays in the sidebar after the directory is removed. Inventory them with `paseo project ls --json`, taking only projects whose `path` equals or lies under a directory recorded as created by this session or its workers; a name that merely resembles the work's names is not ownership, and projects the user or other sessions registered are never touched. Remove the session's own terminals and worktrees under that path first, then delete a project with `paseo project delete <project-id>`, which archives its workspaces and does not delete the directory, only when the same call confirms all of these: the `path` is under a recorded session-created directory, the path no longer exists on disk, no terminal in `paseo terminal ls --all --json` has a `cwd` under it, and no agent in `paseo ls -g --json` has a `cwd` under it. Never delete the project that holds this session's own workspace. Retain and report, with the failed condition, any project that still has its directory, a terminal, or an agent, or whose creator cannot be confirmed. The user's words (2026-11-16), after a session found 15 such projects left by a worker's `paseo terminal create --cwd <measurement worktree>` and reported which were empty registrations: "정리 가능한것만 정리해", and, on adding the same check to this skill: "클린업에도 추가하고" (typed as "클린업에도 추가하가ㅗ").

## Orca resources

In Orca, the session's resources are the objects whose ids a result of its own command named: a workspace from `orca worktree create` (removed through `worktree.py remove`, which hands it to `orca worktree rm` and keeps the branch, as `~/.agents/skills/worktree/SKILL.md` says), a terminal from `orca terminal create` (closed with `orca terminal close --terminal <handle>`), a worker from `orca orchestration worker-start` (a finished one closes on its own unless kept open; release a kept-open one with `orca orchestration worker-release --dispatch <id>` after its output is read, and stop a running one only on the user's word with `orca orchestration worker-stop --dispatch <id>`), and an automation from `orca automations create` (removed with `orca automations remove <id>`, which also removes its run history, so keep what the work needs from `orca automations runs --id <id>` first). Inventory them with `orca worktree list --json`, `orca terminal list --json`, `orca orchestration worker-list --json`, and `orca automations list --json`, take only the ids the session's records name, and leave every other object, including the workspace this session runs in.

## Execution

State the concrete cleanup targets, retained resources, and assets before executing. This preview adds no recurring approval requirement: proceed within the existing authorization, asking only for actions that already require permission.

For every destructive command, confirm the exact target and exclusive session ownership in the same call as deletion. Use recorded exact paths, saved PIDs, container IDs, and image IDs. Do not use broad prune, wildcard deletion, `pkill`, or process-name matching. Inspect image references before removing a session-built image; retain it if any other resource uses it. Remove a session-created worktree only after preserving necessary changes and files and verifying its root and branch. Do not delete the active checkout or the workflow evidence needed to finish the run.

Make repeated invocations converge: check actual existence, recognize already preserved assets by their contents, and report already removed targets without failing or creating duplicate archives or memory entries. Recheck ownership before acting; an old inventory cannot authorize deleting a replacement resource.

Report what was removed, preserved asset paths, retained resources and reasons, and failures or unverified work. Never claim a planned cleanup ran. For workflow completion, also write the execution evidence required by the current finishing stage. pi does not load this skill; a pi worker hands finishing to its orchestrator instead of bypassing cleanup.
