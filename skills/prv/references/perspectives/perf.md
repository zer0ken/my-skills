# Method: performance budget
1. Each computation the design specifies (a query, an aggregation, a selection, a ranking, a search, a numeric routine) is named as its known problem type, with the formal definitions the requirement's words admit and the known algorithms for them and their complexity; a design that picks one of higher complexity than a known algorithm that meets the same requirement is a defect whatever the current input size, such as an all-pairs medoid where the member nearest the centroid takes one pass.
2. List every hot path the design adds or changes (per request, per document, per candidate, per row): its query shape, model calls, embedding calls, and network round trips per unit.
3. Each hot path has a stated budget and the evidence that it holds: a proof of the bound from the code and the documented semantics of the system it runs on, with its premises and their sources, or, where no proof settles it (constants on real data, model latency, behaviour the documentation leaves undefined), a measurement on realistic data size (not test seeds) with the command (EXPLAIN ANALYZE, PROFILE, benchmark).
4. Per-row function calls inside search or batch queries are bounded and indexable; no per-id lookup scans a large table.
5. The feature's model-call work fits the stated time target (one existing LLM call time); identify calls that cannot change the outcome.
6. Comparison with main on the same input is planned for search score and recovery where they are affected, and for upsert time where no proof settles it.
