# Research and controlled PoCs

For practical investigation consult official online documentation, then web search, then internal records when earlier sources leave the question open. Check the installed product, version, extensions and settings actually used. If claiming a feature is absent, check the full installed interface, schemas, catalogs, underlying engine and known solutions. Otherwise report where you looked. A version-matched installed build is primary evidence. Prefer current online documentation to offline copies.

Define input, output, constraints and evaluation criteria in the user's terms. Verify labels and metrics against that definition. Search the field's names for the problem and methods before selecting candidates. Survey primary literature, standard implementations, decision records and original measurements. Use search results as candidates. Check a precedent against the issue, contract, introducing commit and callers, at both the starting revision and current default branch. Repetition is not evidence of correctness.

Build the design from the methods found. Compare the standard implementation against project constraints. For an unnamed combination search for reasons the methods are not combined and record what remains unverified. For each design claim name what would refute it, inspect sources, and report open premises. Include alternatives, numeric sources, measurement limits and uninvestigated scope. When results differ from expectations, investigate the cause before varying the method. Use an independent reviewer when the judgment requires independence.

For a PoC state one concept, divide it into subproblems and test the smallest input that exposes each. Keep the product's split, judgment prompt, output schema, model call, validation and result construction wherever they correspond to the feature. Change only the variable under investigation. Keep the user's unit, models and scope; clarify an ambiguous unit before running. Avoid rebuilding unrelated infrastructure. Check products' version-specific documentation and caveats, and use the established methodology of each domain. Apply its expert skill if available; propose a missing expert skill for approval.

For a performance claim proven by code and documented semantics, write the premises and proof. Measure only unsettled properties such as latency or data-dependent constants. Test functionality separately. For a comparison, fix inputs, environment and all variables except the one compared.
