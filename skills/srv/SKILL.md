# swarm-review (srv)

srv reviews a code change as one review team. A script gathers the repository context once and every session reads it; the change is described per review unit and the yardsticks it is judged by are built over the whole change; one inspector per yardstick reads only that yardstick's targets; a judge decides each yardstick from what the inspectors observed; questions one inspector cannot settle go to the inspectors whose yardsticks hold their target; and the findings are verified against the head before a rule decides the verdict. ## What a review is

A review tests the claim that the change keeps what it must keep, by looking in the repository for counterexamples that break the claim, and decides from the counterexamples it confirmed and the doubts it could not remove. It has two layers. The upper, axiological layer decides what matters: the values the change is judged by. The lower layer decides how the review knows a value was lowered: counterexamples, verified against the code and, where reading cannot decide, run. The lower layer is eliminative argumentation in assurance cases, where confidence in a claim grows as its doubts (defeaters) are found and removed one by one (Goodenough, Weinstock, Klein, https://www.sei.cmu.edu/library/eliminative-argumentation-a-basis-for-arguing-confidence-in-system-properties/; Bloomfield, Netkachova, Rushby, https://arxiv.org/abs/2405.15800v1), so acceptance only ever says "no counterexample within what was searched". The output is one judgment J = (decision, confirmed counterexamples, questions to people, residual risk), not a list of findings, and what was not established is never turned into acceptance. The problem definition this rests on is `~/agent-assets/rebot/PROBLEM-review.md`.

## Relation to prv and rv

prv reviews a plan before code exists; srv reviews a code change (a PR, a branch, or a commit range) the same way, with perspectives picked from its catalog for the change instead of plan checklists. `rv` is one exhaustive adversarial review by one strong reviewer, item by item in consecutive turns with an item ledger; srv is a team of narrow, cheap, blind inspectors whose findings count only after they are verified against the head. srv does not replace rv: the caller may run srv first and give its review document to an rv review as an earlier review, the way prv runs before the rv design review.

## Inputs

1. The head commit and the target branch (or merge base). Create a detached worktree of the head, save `git diff <merge base>...<head>` as `diff.patch` in the review directory, and record its sha256.
2. What the change answers: the issue body and the decisive comments and user decisions, copied into the review directory, so later edits do not change what was reviewed.

Reviewer sessions get nothing else besides the head they read in their jail: no PR body, no PR reviews or replies, no design documents or measurements of the producer, no conversation. The producer's conclusions break the blindness. Earlier reviews of the same change go only to the operator, to mark which clusters are new.

## Perspectives

A perspective is picked from the catalog, never built. After a lead had let code build one perspective per value source, 266 of them on PR #1726, the user said (2026-11-24): "관점은 코드에서 찾는게 아니라 미리 정해진 검토 관점 중에서 코드 변경에 관련된 걸 고르는거다. 똑바로 해르". The earlier definition still holds for what a perspective is, a value-theoretic yardstick with a core value, a depth, and a breadth: "axiology에는 핵심 가치에 대한 정의, 그 가치를 검증할 깊이, 넓이를 한정하지 않으면 정교한 리뷰가 불가능해. 그래서 특정 PR에 있는 diff를 보고, 그 diff에 의해 일어나는 모든 변화를 커버할 수 있는 가치론적인 평가 잣대를 여러개 만들고, 그것이 내가 말한 "관점"이야" (2026-11-24). This skill reads the two together: the core value and the depth come from the catalog, and "만들고" is the review fixing each picked perspective's breadth and binding its `broken_if` to this diff. That reading is the lead's, not the user's words.

Depth is the level of abstraction at which the value is judged, high or low. When the lead answered "깊이가 뭔데" with read, trace, and execute (how far verification goes) and had set tools and sample counts by it, the user said (2026-11-24): "하이레벨 로우레벨을 말한거다." The lists that make the two levels concrete (concepts, data model, responsibilities, module boundaries for high; branches, boundary inputs, single lines for low) are the lead's expansion of that answer, not the user's words. Breadth and depth trade against each other, which is why there are perspectives at all (the user, 2026-11-24): "넓게 보려면 앝게 봐야돼. 좁게 보려면 깊게 봐야돼. 넓고 깊게 보라고 해봤자 어차피 못본다", "그러니까 관점이 필요한거라고". So a catalog perspective has one depth, and one perspective never asks for both.

Breadth is the set of changes a perspective judges, its horizontal span: from the change of one function to every file and backend the change touches. Asked "범위는 뭔대 그럼", a lead answered that breadth is that horizontal span, that depth is the vertical axis, and that R-004 of PR #1726 is caught only by a high-depth yardstick whose breadth covers all six queries, and the user confirmed (2026-11-24): "ㄱㄱ". So breadth is not bound to the review units the diff was cut into.

`bin/design.py` works in two steps, each call starting with the context pack, because the pack already holds what a session would search for (the user, 2026-11-24: "단발 구조화 출력은 좋지. 필요하면 그렇게 해."). First, one call per unit, with the brief `references/changes.md`, writes that unit's changes, each with its kind and the structure it alters or why it alters none, and the repository rules it cites from the pack. Then the perspectives are picked (`build_perspectives`):

1. Code picks every catalog perspective one of whose picks some change has, a kind, `structure`, or a tag the change-set call gave (`stakes_by_pick`), with no model call; a perspective no change picks is left with that reason. REVIEW-TECHNIQUES.md 6.2 puts the picking in code because srv minimises time and this call was on the critical path (the user, 2026-11-25: "srv는 완벽히 리뷰 가능하면서 가장 시간이 빠른 절차여야돼.").
2. Code cuts each picked perspective into tasks: a `high` one takes its whole stake as one task; a `low` one is cut into tasks of at most `design.LOW_BREADTH_MAX` (8) changes, the bound measured on PR #1470, whose low perspectives all had at most 8 changes and held all eight first-review findings, while on PR #1726 low perspectives of up to 42 changes over 24 units ran long and missed findings.
3. One call with `references/rules.md` attaches each cited rule (once per text) to the picked perspectives whose value it refines. A rule is a criterion of a picked perspective and becomes a check's source there, never a perspective of its own, and a task gets only the rules whose document's directory holds one of its files. A rule may be left as context with a reason, except a rule in a subdirectory's rule document whose directory holds a changed file: run 13i left out the one-backend docstring rule that rv R-007 rests on, while run 13l, made to keep every rule, kept 61 root rules as perspectives of their own.
4. One call per task, all at once, with `references/bind.md`, fills the perspective's `broken_if` frame with the names of that task's changes and writes the checks that decide it, each naming its source, the perspective's own value or one attached rule, so a rule's observations stay apart from the value's (in run 13h one `broken_if` that joined four values lost the reuse fact an inspector had observed). A task is bound on its own changes: run 14b bound one `broken_if` per perspective and gave it to every task cut from it, so most tasks judged changes their `broken_if` did not name.

The catalog loader (`sweep.read_catalog`) refuses a catalog in which some change kind is picked by no `low` perspective, a change that alters structure by no `high` one, or an external contract by no `execute` one, so coverage holds by construction whatever list the file holds, and `check_perspectives` asserts it on the assembled set before any inspector runs:

1. Every hunk is in some change-set element or is declared behaviour-free with a reason, so the change set covers the diff.
2. Every perspective is a catalog perspective with its value and depth unchanged and a `broken_if` bound to this change, and every check asks that value or a rule attached to it.
3. Every change-set element is in the breadth of some `low` perspective, so no change is accepted unjudged, and no `low` breadth exceeds the cap.
4. Every structural change is in the breadth of some `high` perspective, because a structural defect judged only at low level shows as its symptoms: on PR #1726 a fixed-perspective srv run caught a wrong result at `graph_search.cypher:339`, while the defect was the record identity kept as a `metadata_pairs` string prefix (rv R-004, `~/agent-assets/rebot/INPUT-rv-vs-srv-records.md`).
5. Every change of kind `external_contract` (what the code assumes an external program, service, or library does) is in the breadth of a perspective with an `execute` check, because reading the code that assumes a contract cannot decide whether the contract holds.
6. Every catalog perspective is picked or left with its reason, and every cited rule is attached or left with its reason under the exception of step 3.

The change set is derived per review unit, because one session cannot hold every hunk of a large change, but the perspectives span the whole change set, so a structure that spans units gets one yardstick whose breadth takes every unit that holds part of it. The pack lists every head line that names what the diff adds, so an inspector sees where one concept is represented, written, or tested without searching for it.

An answer that fails a check goes back to the model once with the problems listed; a unit or a perspective set with no valid answer stops the run (exit 1), because its changes would be reviewed by nobody.

That answer decided how a reviewer applies rv: one reviewer covers rv's criteria in one turn under one perspective, not one item per turn. The catalog's perspectives are REVIEW-TECHNIQUES.md section 4, re-founded on outside review techniques (the user, 2026-11-24: "코드 리뷰 기법을 외부에서 찾고, 그것을 바탕으로 재정립해라."), whose 4.4 maps every former rv item and value file to them, and each names its sources; rv's item ledger and one-item-per-turn rule belong to rv's own reviewing session, not to srv reviewers.

A perspective is a yardstick, not a persona. The user's words (2026-11-12): "전문 작업에서는 '역할극'이 아니라, 메소돌로지를 적용해야돼." ## Team

The team is Fagan's inspection with perspective-based reading. Fagan's process opens with an overview whose objective is "Education" of the whole team, then individual preparation, then the inspection, where "Questions raised are pursued only to the point at which an error is recognized. It is noted by the moderator", and "A team is most effective if it operates with only one objective at a time" (Fagan, "Design and code inspections to reduce errors in program development", IBM Systems Journal 15(3), 1976, https://www.ida.liu.se/~TDDC90/labs/lab-papers/fagan76.pdf). Perspective-based reading gives each member "operational scenarios where members of a review team read a document from a particular perspective", on the assumption "that the combination of different perspectives provides better coverage of the document than the same number of readers using their usual technique", and "each reader is responsible for a narrowly focused view of the document, which should lead to more in-depth analysis" (Basili et al., "The Empirical Investigation of Perspective-Based Reading", 1996, https://www.cs.umd.edu/~mvz/handouts/emp_pbr.pdf). srv maps them as follows; the mapping of the moderator's routing to code is this skill's reading, not the sources' words.

| Inspection element | srv |
| --- | --- |
| overview (education of the team) | the context pack, built once and first in every request |
| perspective scenario (focused view, its questions) | a perspective: value, `broken_if`, fixed breadth, depth, checks |
| inspector, one objective at a time | one omp inspector per perspective, reporting observations, findings, and questions |
| moderator notes the error, routes what one reader raises | the judge decides each value; `team.py` routes questions by breadth to round 2 |
| moderator's report | `verdict.py` and `REVIEW.md` |

The judge exists because the inspector that gathers the facts is a poor judge of them: on PR #1726 an inspector observed a concept tested in five queries with no shared predicate and still called its value kept, while the same model, given only the value and those observations, called it broken in five of five calls (`~/agent-assets/rebot/srv-team-poc/`).

## Execution

Each check is decided by its means: `read` by reading, `trace` by following the behaviour with the reviewer's tools to where it ends, `execute` by running. Every review session has the read tools and `sandbox_run`, whatever its perspective's depth, because a high value may need a run (two records the data model should keep unique) and a low value may be decided by reading. The user's words (2026-11-24), after a lead reported as a limit that the review sessions had only read tools and could not run tests: "실제 실행도 가능해야돼. 에이전트 하네스를 사용하는데 그걸 못할 이유가 없어". The change is still untrusted input, so its code runs in a different namespace from the session that talks to the model, at two levels:

1. The reviewer jail (`bin/reviewer.py`) holds the omp session. It reads the head but cannot write it, its working directory is empty because omp discovers extensions, rules, and context files from the working directory ("Project directory: `<cwd>/.omp/extensions`", omp://extension-loading.md) and discovery is also off by flag, its agent directory is generated with one provider so the caller's `~/.omp` is not mounted, its environment is cleared, and it has no network but the model relay. This follows sandbox-runtime on Linux: "The network namespace of the sandboxed process is removed entirely, so all network traffic must go through the proxies running on the host (listening on Unix sockets that are bind-mounted into the sandbox)" (https://github.com/anthropic-experimental/sandbox-runtime). The relay forwards bytes to the one model server, so it needs no domain allowlist.
2. `sandbox_run`, offered to every review session (not to the design session, which runs nothing), starts `bin/sandbox.py` from inside the jail: a nested bubblewrap with every namespace unshared, a fresh copy of the head's tracked files, the environment cleared, and neither the relay socket nor the agent directory mounted. A script there cannot reach the model, the network, the session's process, or the head itself, and every call starts from the unmodified head. The reviewer writes and runs its counterexample there and iterates on it, the way LIBRO and Agentless generate reproduction tests and keep the ones that execution confirms ("Agentless then generates reproduction tests to verify that the issue has been resolved", https://arxiv.org/abs/2407.01489; LIBRO: "rank the produced tests according to their validity", https://arxiv.org/abs/2209.11515).

Dependencies are prepared before, outside both, without running the change's build or install scripts, and passed with `--sandbox-ro` to the scripts and `--ro` to `sandbox.py`. A counterexample that rests on how an external program, service, or library behaves is decided by a fake that returns what the system's official documentation says, or by quoting that documentation; a live external system is not probed, and when neither decides it the cluster stays PLAUSIBLE and its check is not decided. A reviewer's account of a run is a claim: `team.py` does not re-run the inspectors' scripts, so a cluster resting on a run is graded `read` from the head lines its verify calls saw, never `executed`.

## Stages

Each stage names its input, its output, who decides, when it stops, what happens when it fails, and what the next stage relies on. `bin/team.py` runs them in order and writes each stage's wall time and the model server's prefill and decode seconds (from its `/metrics` histograms) to `team-summary.json` as the stage ends.

| Stage | Input | Output | Decided by | Stops when | On failure | Next stage relies on |
| --- | --- | --- | --- | --- | --- | --- |
| 1 Prepare | head, target branch, requirement copies | head worktree, `diff.patch` and sha256, `units.json` (`rv/bin/plan-units.py`) | operator, scripts | every hunk is in one unit | stop and report the missing input | every later file records the diff's sha256 |
| 2 Context | units, diff, head, requirements | `context/pack.md`, `pack.json` | script (`context.py`) | written | exit 2 on a diff that is not the plan's | every request starts with the same pack |

## Procedure

1. Prepare the review directory: the head worktree, `diff.patch` with its sha256, and the requirement copies. Resolve the merge base with `git merge-base` and write the full SHA the command printed, never a hand-copied one. Plan the units with `python3 -I ~/.agents/skills/rv/bin/plan-units.py --diff diff.patch --repo <head worktree> --out units.json`, and read its summary line (units, files, excluded) before going on; an excluded file is listed with its reason and is not reviewed.
2. Before loading the model server, check that it answers (`curl -sS -m 5 <server>/v1/models`) and whether another session is measuring on it (an open `run-*` terminal of another session that calls it, as the harness instructions require). Launch only when the check succeeded, chaining the launch on its exit code. When a measurement is running, ask the user whether to launch now and wait for the answer; the answer covers that run only. Asked whether srv should get a standing exception from the harness's measurement check, the user answered (2026-11-15) "앞으로도 확인하고 나한테 물어보도록 해 그럼". Record the server state (`vllm:num_requests_running`, `vllm:num_requests_waiting`) in the procedure log.
3. Run the team in one runtime terminal of the operator's workspace (Paseo or Orca, as `~/.agents/skills/agent-runtime/SKILL.md` maps) named `run-srv-<target>-<run number>`, ending the command line with the exit code written to a file: `uv run ~/.agents/skills/srv/bin/team.py --units units.json --diff diff.patch --repo <head worktree> --requirements <copies> --out <review dir> --base-url <server>/v1 --model <model> [--api-key-env <variable>] [--sandbox-ro <prepared environment>] [--inspect-timeout <seconds>]`. It needs `omp` and `bwrap` on PATH. Wait for it in the same turn: an omp operator started in print mode (`omp -p`) is started by its caller with `--wait-async` ("Print mode: before exiting, wait for this run's background jobs and wake the session with each result", `omp --help`, omp 19.1.1), because in run 11a an omp operator put `team.py` in a background job, ended its turn, and the job ended with the session during the design stage. Dependencies for counterexample runs are prepared before, outside the sandbox, without running the change's build or install scripts (`uv sync --frozen --no-build`, `npm ci --ignore-scripts`, `cargo fetch`), and passed with `--sandbox-ro`.
4. When `team.py` exits 1, a stage left part of the change unreviewed; its message names the part and the rerun. Remove the cause (endpoint, token limit, schema, an uncovered hunk) and run again; a failure is never dropped from the review or treated as reviewed, and a design is never written by hand around the coverage check.
5. Read `REVIEW.md` and `team-summary.json`. The decision is the one `judgment.json` holds.
6. Remove the head worktree with `git worktree remove`; the review directory keeps every input and output.
7. End the operator's turn with the decision, the counts of confirmed clusters per severity, the residual risks in one line each, the stage times, and the path of `REVIEW.md`, under 4,000 characters. Accepting, rejecting, posting, and fixing are the caller's; the caller handles the CONFIRMED and PLAUSIBLE clusters as one round of findings with the `response-rv` skill, and when the root cause of a criticism of `REVIEW.md` lies in this procedure, fixes srv.

The operator edits nothing but the review directory and the head worktree it created: no tracked-file edits, commits, pushes, PR or issue comments, posted reviews, or messages to people. Inspectors have no tool that writes, sends, or starts sessions, and run the change's code only inside the sandbox. The operator does not stop or restart a model server.

A `high` perspective of wide breadth asks only what its bound checks name: on #1726 the reuse perspective held the change of rv R-008 but no check named the function, and the inspector did not judge it.

Not done by `team.py`, though the earlier operator procedure did them: questions to people are always empty, open issues are not searched before a finding is called OUT-OF-SCOPE (OUT-OF-SCOPE was 0 in every run), and verification rejected 1 of 47, 0 of 43, 0 of 19, and 1 of 38 findings, so how many CONFIRMED clusters outside the gold findings are true was not checked.
