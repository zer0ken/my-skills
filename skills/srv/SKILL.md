# swarm-review (srv)

srv reviews a code change with a swarm. A script splits the change into review units; a design call per unit says what the change makes different and builds the yardsticks it is judged by; one call to the self-hosted model per unit and perspective reviews it; one operator session verifies every suggestion against the code, runs what reading cannot decide, digs further with follow-up rounds, and hands one review document with its decision to the caller. The user's words (2026-11-15): "이거 /prv 참고해서, /prv와 같은 방법으로 pi 세션 많이 띄워서 코드에 대해 /rv하게 만들어. 그리고 들어오는 제안은 코덱스가 정리하고, 더 자세히 파기 위해 추가로 리뷰를 계속 해서, 결과적으로 하나의 리뷰 문서를 너한테 가져오라고 해. 이 과정을 /swarm-review , 줄여서 /srv라는 스킬로 저장해. 코덱스 세션 띄우는거 말고 그 다음 부분부터". On 2026-11-24, after the rebot review bot that had grown from this method was abstracted into review, perspective, and bot, the user said: "rebot 자체는 폐기하자. 그 대신 srv 스킬을 고도화하는 것으로 하자", so srv now carries rebot's definition of a review.

The skill's directory is `srv` and its `name` is `swarm-review`, so Claude Code takes both `/swarm-review` and `/srv`: "In a personal or project skill directory, `name` sets the command that the `/` menu shows and that you type, unless another command already uses that name. The caller, the operator, and the reviewers follow `## Caller and operator` of `~/.agents/skills/prv/SKILL.md` as written: the caller starts exactly one operator, the operator runs every reviewer below it and verifies and consolidates their suggestions itself, it archives each reviewer session once its round has finished, and the caller archives the operator after reading its report. The caller's brief gives the head and the target branch (or merge base), the requirement copies, the review directory, and the earlier reviews when there are any. srv names no agent for the operator; asked who the operator should be, the user answered (2026-11-15): "이건 특정 에이전트를 위한 스킬이 아니다." The session that runs srv is the operator, whichever agent the caller chose under its own role rules.

## What a review is

A review tests the claim that the change keeps what it must keep, by looking in the repository for counterexamples that break the claim, and decides from the counterexamples it confirmed and the doubts it could not remove. It has two layers. The upper, axiological layer decides what matters: the values the change is judged by. The lower layer decides how the review knows a value was lowered: counterexamples, verified against the code and, where reading cannot decide, run. The lower layer is eliminative argumentation in assurance cases, where confidence in a claim grows as its doubts (defeaters) are found and removed one by one (Goodenough, Weinstock, Klein, https://www.sei.cmu.edu/library/eliminative-argumentation-a-basis-for-arguing-confidence-in-system-properties/; Bloomfield, Netkachova, Rushby, https://arxiv.org/abs/2405.15800v1), so acceptance only ever says "no counterexample within what was searched". The output is one judgment J = (decision, confirmed counterexamples, questions to people, residual risk), not a list of findings, and what was not established is never turned into acceptance. The problem definition this rests on is `~/agent-assets/rebot/PROBLEM-review.md`.

## Relation to prv and rv

prv reviews a plan before code exists; srv reviews a code change (a PR, a branch, or a commit range) the same way, with perspectives built for the change instead of plan checklists. `rv` is one exhaustive adversarial review by one strong reviewer, item by item in consecutive turns with an item ledger; srv is a wide, cheap, blind sweep whose suggestions count only after the operator verifies them. srv does not replace rv: the caller may run srv first and give its review document to an rv review as an earlier review, the way prv runs before the rv design review.

## Concepts

| Name | Definition |
| --- | --- |
| change | The code under review: the diff from the merge base to the head commit |
| head | The commit under review, checked out as a detached worktree that every session reads |
| merge base | `git merge-base <head> <target branch>`; the diff is taken from it, not from the commit the work started on |
| review unit | A group of changed files reviewed together, decided by `~/.agents/skills/rv/bin/plan-units.py`; every hunk of the change is in exactly one unit |
| change set | E(Δ), the behaviours the change makes different, per unit: each element (`E-n`) is what a user of the code observes differently (a returned value, stored data, state and ownership, a failure result, resource use, an interface or name, a documented promise, a test contract), with its before, its after, and the hunks that produce it. A hunk that changes no behaviour is declared behaviour-free with a reason |
| perspective | A value-theoretic yardstick built for this change (`K-n`): a core value that must hold, the breadth (the change-set elements it judges), the depth (`read`, `trace`, or `execute`: how far verification must go before the value is decided), the checks that decide it, and its sources |
| value catalog | The universal value sources srv carries, one method file per entry under `references/values/`, made of named rv review items and `-expert` sections; a perspective's value comes from the requirement copies, a repository rule, or catalog entries |
| design | One unit's change set and perspectives, written by `bin/design.py` to `design/<unit>.json` after its coverage check passed |
| task | One review unit and one perspective designed for it; round 1 has one task per pair |
| sample | One independent round-1 call for a task; a task runs `--samples` of them at once (default 3) and pools their findings, each marked with its sample number |
| reviewer | In round 1, one structured-output model call that reviews one task, one of its samples (`bin/sweep.py`); in later rounds, a self-hosted-model session that answers one follow-up question. Each is blind to everything but its inputs |
| anchor | The verbatim head line a finding points at; `bin/anchor-findings.py` re-locates the finding's line from it |
| operator | The session that runs srv: prepares inputs, launches the design and the reviewers, verifies and clusters every suggestion, runs counterexamples, writes follow-up questions, decides the verdict by rule, and writes the review document |
| suggestion | One finding a reviewer reports; it is not a defect until the operator verifies it |
| scope | The promise of the change, as rv's `## Scope of a finding` (`~/.agents/skills/rv/SKILL.md`) defines it; a suggestion outside it is not a finding (verdict OUT-OF-SCOPE) |
| cluster | A group of suggestions the operator judged to describe the same defect, with one verdict: CONFIRMED, PLAUSIBLE, or REJECTED, and an evidence grade: `executed`, `documented`, `traced`, or `read` |
| counterexample run | One run of the head's own code, driven into the situation a suggestion names, inside the sandbox; its directory holds the script, `run.json`, and the output |
| sandbox | `bin/sandbox.py`: bubblewrap with every namespace unshared (no network), the caller's environment cleared (no token), no home directory, no `/run` or `/var` (no daemon socket), and a writable copy of the head's tracked files |
| round | One launch of reviewers followed by the operator's verification of their output; round 1 is the task sweep, later rounds answer follow-up questions |
| follow-up question | A narrow question the operator writes from a verified round, sent to new reviewers to dig into one place |
| verdict | The judgment J that `bin/verdict.py` decides from `verdict.json`: 차단, 증거 부족, 조건부 수용, or 수용, with the confirmed clusters, the questions to people, and the residual risk |
| residual risk | What the review did not establish: PLAUSIBLE clusters and perspectives whose depth was not reached |
| review document | The one Markdown file srv returns to the caller |

## Inputs

1. The head commit and the target branch (or merge base). Create a detached worktree of the head, save `git diff <merge base>...<head>` as `diff.patch` in the review directory, and record its sha256.
2. What the change answers: the issue body and the decisive comments and user decisions, copied into the review directory, so later edits do not change what was reviewed.

Reviewers and the design call get nothing else: no PR body, no PR reviews or replies, no design documents or measurements of the producer, no conversation. The producer's conclusions break the blindness. Earlier reviews of the same change go only to the operator, to mark which clusters are new.

## Perspectives

A perspective is built for each change, not chosen from a list. The user's definition (2026-11-24), given after a lead had answered that a perspective was "one defect question" and then quoted this skill's earlier definition ("rv 항목을 묶은 점검 목록"), and after the user asked for review to be defined as a technical problem: "나는 axiology를 바탕으로 해결하려고 했어." and "axiology에는 핵심 가치에 대한 정의, 그 가치를 검증할 깊이, 넓이를 한정하지 않으면 정교한 리뷰가 불가능해. 그래서 특정 PR에 있는 diff를 보고, 그 diff에 의해 일어나는 모든 변화를 커버할 수 있는 가치론적인 평가 잣대를 여러개 만들고, 그것이 내가 말한 "관점"이야".

`bin/design.py` builds them with one structured-output call per unit, the brief `references/design.md`, and the value catalog, and checks in code what the definition requires before any reviewer runs:

1. Every hunk is in some change-set element or is declared behaviour-free with a reason, so the change set covers the diff.
2. Every change-set element is in the breadth of some perspective: the union of the breadths is the change set, so no change is accepted unjudged.
3. Every catalog entry is the source of some perspective or is dismissed with the reason nothing in the unit is at stake for it. This is the other direction of coverage: a test contract the change left unpinned, or a name that misstates its unit, is not a behaviour change and could pass the first two checks under one catch-all perspective.

An answer that fails a check goes back to the model once with the problems listed; a unit with no valid design stops the run (exit 1), because its changes would be reviewed by nobody.

The earlier decision still holds where it answered. It did not decide that perspectives are a fixed list, so the rv items now live in the value catalog, and each perspective names the catalog entries its value comes from; the reviewer gets their checklists as its method. rv's item ledger and one-item-per-turn rule belong to rv's own reviewing session, not to srv reviewers.

A perspective is a yardstick, not a persona. The user's words (2026-11-12): "전문 작업에서는 '역할극'이 아니라, 메소돌로지를 적용해야돼." ## Execution

The depth of a perspective decides how its checks are settled: `read` by the operator's reading, `trace` by follow-up questions to sessions with tools, `execute` by running. The user's words (2026-11-24), after a lead reported as a limit that the review sessions had only read tools and could not run tests: "실제 실행도 가능해야돼. 에이전트 하네스를 사용하는데 그걸 못할 이유가 없어". The change is still untrusted input, so the operator runs its code only inside `bin/sandbox.py`, apart from every session that talks to a model: no network, not even the host's loopback or the model server; no caller environment, so no token; no home directory; no `/run` or `/var`, so no daemon socket; and a copy of the head's tracked files, so the head worktree is never written. Dependencies are prepared before, outside the sandbox, without running the change's build or install scripts, and mounted read-only. A counterexample that rests on how an external program, service, or library behaves is decided by a fake that returns what the system's official documentation says, or by quoting that documentation; a live external system is not probed from the sandbox, and when neither decides it the cluster stays PLAUSIBLE and the perspective's depth is not reached. `references/consolidate.md` step 3 holds the procedure.

## Review workspace

The follow-up reviewer sessions of rounds 2 and later run in a review workspace of their own, so they do not fill the caller's workspace, which the operator runs in. The user's words (2026-11-14), said of prv when its reviewers were sessions: "Prv는 호출된 파세오 프로젝트 안에 새 워크스페이스를 만들고 그 안에 필요한 세션들을 모두 소환해줘" and "그리고 끝나면 자동으로 워크스페이스를 보관햐줘".

1. Find the project: the operator's own `workspaceId` is in `get_agent_status` for its own agent id (confirm the snapshot is its own, because `PASEO_AGENT_ID` can name the session that launched it), and that workspace's `projectId` is in `list_workspaces`. The operator runs in the caller's workspace, so this is the caller's project.
2. Before round 2, create the review workspace with `create_workspace`: `isolation: "local"`, `path` the head worktree, `projectId` the project of step 1, `title` `srv <target> <run number>`. Pass the `projectId` explicitly: a local workspace on a subdirectory is otherwise registered as a project of its own. Create each reviewer session with `create_agent` and `workspaceId` the review workspace; a session placed there stays the operator's subagent (Paseo docs, MCP "Mental model": "Passing a `workspaceId` places that subagent in another workspace without detaching it from its parent."), so its finish notification reaches the operator and stops there.
3. When the run ends, whether finished or abandoned, confirm that no session in the review workspace has a running turn (`get_agent_status`), then `archive_workspace` it. Archiving a local workspace leaves its directory (`removedDirectory: false`), and the review files live outside it, so remove the head worktree afterwards with `git worktree remove`. The operator never archives the workspace it runs in: that is the caller's, and the caller archives the operator.

In Orca, the review workspace is an Orca workspace on the head: create the head worktree with `orca worktree create --name srv-<target>-<run number> --base-branch <head ref> --json` (nested under the operator's workspace by default, "Orca records the new worktree as a child of the caller context") and prepare it with `worktree.py prepare <path>`; start each reviewer with `orca orchestration worker-start --environment local --worktree <its selector> --agent claude --spec-file <brief>`, whose `worker_done` mail reaches the operator; when the run ends and `orca orchestration worker-list` shows no reviewer working, remove it with `orca worktree rm`, which keeps the branch.

Outside a runtime there is no workspace to create; launch the sessions as the harness allows and skip this section.

## Procedure

1. Prepare the review directory: the head worktree, `diff.patch` with its sha256, and the requirement copies. Resolve the merge base with `git merge-base` and write the full SHA the command printed, never a hand-copied one: in the first run a mistyped 41-character SHA stopped a reviewer. Plan the units with `python3 -I ~/.agents/skills/rv/bin/plan-units.py --diff diff.patch --repo <head worktree> --out units.json`, and read its summary line (units, files, excluded) before going on; an excluded file is listed with its reason and is not reviewed.
2. Before loading the model server, check that it answers (`curl -sS -m 5 <server>/v1/models`) and whether another session is measuring on it (an open `run-*` terminal of another session that calls it, as the harness instructions require). Launch only when the check succeeded, chaining the launch on its exit code: in the first run a failed check did not stop the launch. When a measurement is running, ask the user whether to launch now and wait for the answer; the answer covers that run only. Asked whether srv should get a standing exception from the harness's measurement check, the user answered (2026-11-15) "앞으로도 확인하고 나한테 물어보도록 해 그럼", which replaced the earlier answer "항상 응답 확인만". Record in the procedure log the server state (for vLLM, `vllm:num_requests_running` and `vllm:num_requests_waiting` from `/metrics`), the user's answer, and how many requests or sessions were launched at what time, so a measurement on that server can account for the load.
3. Design and round 1, chained in one runtime terminal of the operator's workspace (Paseo or Orca, as `~/.agents/skills/agent-runtime/SKILL.md` maps) named `run-srv-<target>-<run number>`, ending the command line with the exit code written to a file, as the harness instructions require for a long run: `uv run ~/.agents/skills/srv/bin/design.py --units units.json --diff diff.patch --repo <head worktree> --requirements <copies> --out design --base-url <server>/v1 --model <model> --api-key-env <variable> && uv run ~/.agents/skills/srv/bin/sweep.py --units units.json --diff diff.patch --repo <head worktree> --design design --requirements <copies> --out round-1 --base-url <server>/v1 --model <model> --api-key-env <variable>`. The design call per unit writes `design/<unit>.json` once its coverage check passes (section Perspectives); the sweep then sends `--samples` independent structured-output requests per task (default 3), all in parallel up to `--max-concurrency` (default 128, a cap on this client and not the server's capacity, which the server enforces by queueing or refusing calls). Each request carries the brief `references/brief.md`, the perspective (value, depth, the change-set elements of its breadth, checks, and the catalog entries it rests on), the requirement copies, the unit's hunks, the unit's head files with line numbers, and the lines elsewhere at the head that name a symbol the unit changes. A call the server refuses (HTTP 429, 502, 503, 504, or a refused or dropped connection) waits, with capped exponential backoff and full jitter or the server's `Retry-After`, and is sent again until the server answers or 15 minutes pass, without using an attempt, because on 2026-11-20 the vllm-router on 100.99.0.1:8000 opened its circuit breaker for 61 s after send errors to its workers, and 197 of 234 tasks failed when both attempts of each call came back refused within one second; each wait is recorded in the task's `errors`. Each answer is validated, retried once when invalid, and its lines are re-located from their anchors; a task is valid only when every sample is, and each task writes `round-1/<unit>__<perspective>.json`, and the run writes `summary.json` and `progress.json`.
4. `design.py` and `sweep.py` exit 1 when a unit has no valid design or a task has no valid output, because that unit, or that perspective of it, is then unreviewed. Read the file's `errors`, remove the cause (endpoint, token limit, schema, an uncovered hunk), and rerun only those with `--only`; the summary then counts every unit or task of the plan again. A failure is never dropped from the review or treated as reviewed, and a design is never written by hand around the coverage check.
5. While the sweep runs, read the designs: a value the change plainly puts at stake that no perspective holds becomes a follow-up question of round 2 (`references/deepen.md`), not an edit of the design.
6. Verify the round by `references/consolidate.md`: take the suggestions from the task files, open every cited `file:line` at the head (the line `anchor-findings.py` re-located; `anchor_status` says how), give each suggestion a verdict, cluster, and re-grade severity; run in the sandbox every suggestion that only a run decides, starting with those of `execute` perspectives. Agreement is not evidence: judge a cluster by the code, never by how many tasks raised it.
7. Write follow-up questions by `references/deepen.md`, including the undecided checks of `trace` perspectives, and launch round `k` (k ≥ 2): one new reviewer session per question in the review workspace (section Review workspace), with the head worktree's pyright and Serena configs prepared by `worktree.py prepare` of `~/.agents/skills/worktree/SKILL.md` (in the first run the unprepared worktree under the ignored `.worktrees/` path made every reviewer fall back to text search). Each session gets the blind inputs, the question, and the follow-up brief in `references/deepen.md`, and writes `round-<k>/Q<n>-result.md`. Wait inside the turn with `paseo wait <id> --timeout <seconds>` ("Block until an agent finishes its current task", https://paseo.sh/docs/cli, checked 2026-11-17), one session after another, repeating the call when it returns on the timeout, with the timeout inside the shell tool's limit; in Orca, wait with `orca orchestration check --wait --types worker_done --timeout-ms <ms>`, which blocks until a reviewer's report arrives and returns it, and repeat it until every reviewer of the round has reported. When every session of the round has finished, archive each with `archive_agent`, then verify the round as in step 6, merging its suggestions into the existing clusters.
8. Stop when a round adds no new CONFIRMED cluster and every perspective has reached its depth or is recorded as not reached with the reason, or after round 3, whichever comes first.
9. Decide the verdict: write `verdict.json` and run `bin/verdict.py`, as `## Verdict` of `references/consolidate.md` says. The decision is the one it prints.
10. Write the review document `REVIEW.md` in the review directory, in the format of `references/consolidate.md`, and `procedure-log.md` beside it: steps, the design and round-1 `summary.json` numbers, the counterexample runs, sessions per later round with launch and finish times, server state, blockers and what was changed. A time box given to a reviewer is recorded against its actual finish time; it is not a stop, and an overrun is written, not hidden.
11. When later rounds ran, archive the review workspace and remove the head worktree with `git worktree remove`, as step 3 of the Review workspace section says.
12. End the operator's turn with the decision, the counts of confirmed clusters per severity, the residual risks in one line each, the count of new confirmed clusters per round, the precision per round, and the path of `REVIEW.md`, under 4,000 characters. An OUT-OF-SCOPE suggestion reaches the caller only as a count. The caller reads `REVIEW.md`; accepting, rejecting, posting, and fixing are the caller's, and the caller handles the confirmed and PLAUSIBLE clusters as one round of findings with the `response-rv` skill. A criticism of `REVIEW.md` itself (a wrong verdict, a missed cluster, weak evidence) is also handled with `response-rv`, and when its root cause lies in this procedure or its references, fix srv so the same defect does not recur.

The operator edits nothing but the review directory and the ignored analysis configs of the head worktree it created: no tracked-file edits, commits, pushes, PR or issue comments, posted reviews, or messages to people. It runs the change's code only inside the sandbox. Follow-up reviewers do not start other sessions; their brief says so. The operator does not stop or restart a model server.

Precision is CONFIRMED / (CONFIRMED + REJECTED) per suggestion; it measures how often a suggestion was true, not how many defects the review found. prv's plan trials and the srv runs agree on one point: agreement among reviewers was not evidence.
