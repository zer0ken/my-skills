# swarm-review (srv)

srv reviews a code change with a swarm. A script splits the change into review units; a reviewer session per unit says what that part of the change makes different, and one session builds the yardsticks the whole change is judged by; reviewer sessions per perspective review it, reading the repository and, where a value is decided by running, running counterexamples; one operator session verifies every suggestion against the code, re-runs what the reviewers ran, digs further with follow-up rounds, and hands one review document with its decision to the caller. Every reviewer session is an omp agent session on the self-hosted model: asked whether srv runs on omp, a lead answered that round 1 was a single model call and asked whether to add omp, and the user said (2026-11-24) "rebot을 srv로 옮긴다니까 뭐하냐?"; rebot's reviewers had been pi sessions with tools, and the user had decided on 2026-11-21 "당분간, pi 대신 omp를 쓰자". The user's words (2026-11-15): "이거 /prv 참고해서, /prv와 같은 방법으로 pi 세션 많이 띄워서 코드에 대해 /rv하게 만들어. 그리고 들어오는 제안은 코덱스가 정리하고, 더 자세히 파기 위해 추가로 리뷰를 계속 해서, 결과적으로 하나의 리뷰 문서를 너한테 가져오라고 해. 이 과정을 /swarm-review , 줄여서 /srv라는 스킬로 저장해. 코덱스 세션 띄우는거 말고 그 다음 부분부터". On 2026-11-24, after the rebot review bot that had grown from this method was abstracted into review, perspective, and bot, the user said: "rebot 자체는 폐기하자. 그 대신 srv 스킬을 고도화하는 것으로 하자", so srv now carries rebot's definition of a review.

The skill's directory is `srv` and its `name` is `swarm-review`, so Claude Code takes both `/swarm-review` and `/srv`: "In a personal or project skill directory, `name` sets the command that the `/` menu shows and that you type, unless another command already uses that name. The directory name also invokes the skill." (https://code.claude.com/docs/en/skills, "How a skill gets its command name").

The caller and the operator follow `## Caller and operator` of `~/.agents/skills/prv/SKILL.md`: the caller starts exactly one operator, the operator runs every reviewer below it and verifies and consolidates their suggestions itself, and the caller archives the operator after reading its report. srv's reviewers are not runtime sessions: each is one `omp -p` process that a script of this skill starts and that ends with its answer, so there is no reviewer to archive and no review workspace to create. The caller's brief gives the head and the target branch (or merge base), the requirement copies, the review directory, and the earlier reviews when there are any. srv names no agent for the operator; asked who the operator should be, the user answered (2026-11-15): "이건 특정 에이전트를 위한 스킬이 아니다." The session that runs srv is the operator, whichever agent the caller chose under its own role rules.

## What a review is

A review tests the claim that the change keeps what it must keep, by looking in the repository for counterexamples that break the claim, and decides from the counterexamples it confirmed and the doubts it could not remove. It has two layers. The upper, axiological layer decides what matters: the values the change is judged by. The lower layer decides how the review knows a value was lowered: counterexamples, verified against the code and, where reading cannot decide, run. The lower layer is eliminative argumentation in assurance cases, where confidence in a claim grows as its doubts (defeaters) are found and removed one by one (Goodenough, Weinstock, Klein, https://www.sei.cmu.edu/library/eliminative-argumentation-a-basis-for-arguing-confidence-in-system-properties/; Bloomfield, Netkachova, Rushby, https://arxiv.org/abs/2405.15800v1), so acceptance only ever says "no counterexample within what was searched". The output is one judgment J = (decision, confirmed counterexamples, questions to people, residual risk), not a list of findings, and what was not established is never turned into acceptance. The problem definition this rests on is `~/agent-assets/rebot/PROBLEM-review.md`.

## Relation to prv and rv

prv reviews a plan before code exists; srv reviews a code change (a PR, a branch, or a commit range) the same way, with perspectives built for the change instead of plan checklists. `rv` is one exhaustive adversarial review by one strong reviewer, item by item in consecutive turns with an item ledger; srv is a wide, cheap, blind sweep whose suggestions count only after the operator verifies them. srv does not replace rv: the caller may run srv first and give its review document to an rv review as an earlier review, the way prv runs before the rv design review.

| counterexample run | One run of the head's own code, driven into the situation a suggestion names, inside the sandbox; its directory holds the script, `run.json`, and the output |

| follow-up question | A narrow question the operator writes from a verified round, sent to new reviewers to dig into one place |

| review document | The one Markdown file srv returns to the caller |

## Inputs

1. The head commit and the target branch (or merge base). Create a detached worktree of the head, save `git diff <merge base>...<head>` as `diff.patch` in the review directory, and record its sha256.
2. What the change answers: the issue body and the decisive comments and user decisions, copied into the review directory, so later edits do not change what was reviewed.

Reviewer sessions get nothing else besides the head they read in their jail: no PR body, no PR reviews or replies, no design documents or measurements of the producer, no conversation. The producer's conclusions break the blindness. Earlier reviews of the same change go only to the operator, to mark which clusters are new.

## Perspectives

A perspective is built for each change, not chosen from a list. The user's definition (2026-11-24), given after a lead had answered that a perspective was "one defect question" and then quoted this skill's earlier definition ("rv 항목을 묶은 점검 목록"), and after the user asked for review to be defined as a technical problem: "나는 axiology를 바탕으로 해결하려고 했어." and "axiology에는 핵심 가치에 대한 정의, 그 가치를 검증할 깊이, 넓이를 한정하지 않으면 정교한 리뷰가 불가능해. 그래서 특정 PR에 있는 diff를 보고, 그 diff에 의해 일어나는 모든 변화를 커버할 수 있는 가치론적인 평가 잣대를 여러개 만들고, 그것이 내가 말한 "관점"이야".

Depth is the level of abstraction at which the value is judged, high or low. When the lead answered "깊이가 뭔데" with read, trace, and execute (how far verification goes) and had set tools and sample counts by it, the user said (2026-11-24): "하이레벨 로우레벨을 말한거다." The lists that make the two levels concrete (concepts, data model, responsibilities, module boundaries for high; branches, boundary inputs, single lines for low) are the lead's expansion of that answer, not the user's words. How a check is decided, by reading, tracing, or running, is the check's means and is chosen per check.

Breadth is the set of changes a perspective judges, its horizontal span: from the change of one function to every file and backend the change touches. Asked "범위는 뭔대 그럼", a lead answered that breadth is that horizontal span, that depth is the vertical axis, and that R-004 of PR #1726 is caught only by a high-depth yardstick whose breadth covers all six queries, and the user confirmed (2026-11-24): "ㄱㄱ". So breadth is not bound to the review units the diff was cut into.

`bin/design.py` builds them in two steps. First, one reviewer session per unit, with read tools and the brief `references/changes.md`, writes that unit's changes, each with the structure it alters or why it alters none, and the repository rules it read. Then one session for the whole change, with the brief `references/design.md`, the value catalog, the requirement copies, those rules, and every unit's changes, builds the perspectives, whose breadth names changes of any units. The script checks in code what the definition requires before any reviewer runs:

1. Every hunk is in some change-set element or is declared behaviour-free with a reason, so the change set covers the diff.
2. Every change-set element is in the breadth of some `low` perspective, so the union of the breadths is the change set and no change is accepted unjudged.
3. Every change-set element states its structure: the concept, data model, responsibility, or module boundary it alters, or why it alters none, the way a behaviour-free hunk states its reason. Every structural change is also in the breadth of some `high` perspective, because a structural defect judged only at low level shows as its symptoms: on PR #1726 of the same repository a fixed-perspective srv run caught a wrong result at `graph_search.cypher:339`, while the defect was the record identity kept as a `metadata_pairs` string prefix, which makes every lookup unwind all documents, leaves uniqueness unenforced by the database, and scatters the prefix test over six queries (rv R-004, `~/agent-assets/rebot/INPUT-rv-vs-srv-records.md`).
4. Every change of kind `external_contract` (what the code assumes an external program, service, or library does) is in the breadth of a perspective with an `execute` check, because reading the code that assumes a contract cannot decide whether the contract holds.
5. Every catalog entry is the source of some perspective or is dismissed with the reason nothing in the unit is at stake for it. This is the other direction of coverage: a test contract the change left unpinned, or a name that misstates its unit, is not a behaviour change and could pass the checks above under one catch-all perspective.

The change set is derived per review unit, because one session cannot hold every hunk of a large change, but the perspectives are built over the whole change set, so a structure that spans units gets one yardstick whose breadth takes every unit that holds part of it. Every reviewer also gets the file list of the whole change and searches the head for the other places that represent the same concept.

An answer that fails a check goes back to the model once with the problems listed; a unit with no valid design stops the run (exit 1), because its changes would be reviewed by nobody.

## Execution

Each check is decided by its means: `read` by reading, `trace` by following the behaviour with the reviewer's tools to where it ends, `execute` by running. Every review session has the read tools and `sandbox_run`, whatever its perspective's depth, because a high value may need a run (two records the data model should keep unique) and a low value may be decided by reading. The user's words (2026-11-24), after a lead reported as a limit that the review sessions had only read tools and could not run tests: "실제 실행도 가능해야돼. 에이전트 하네스를 사용하는데 그걸 못할 이유가 없어". The change is still untrusted input, so its code runs in a different namespace from the session that talks to the model, at two levels:

1. The reviewer jail (`bin/reviewer.py`) holds the omp session. It reads the head but cannot write it, its working directory is empty because omp discovers extensions, rules, and context files from the working directory ("Project directory: `<cwd>/.omp/extensions`", omp://extension-loading.md) and discovery is also off by flag, its agent directory is generated with one provider so the caller's `~/.omp` is not mounted, its environment is cleared, and it has no network but the model relay. This follows sandbox-runtime on Linux: "The network namespace of the sandboxed process is removed entirely, so all network traffic must go through the proxies running on the host (listening on Unix sockets that are bind-mounted into the sandbox)" (https://github.com/anthropic-experimental/sandbox-runtime). The relay forwards bytes to the one model server, so it needs no domain allowlist.
2. `sandbox_run`, offered to every review session (not to the design session, which runs nothing), starts `bin/sandbox.py` from inside the jail: a nested bubblewrap with every namespace unshared, a fresh copy of the head's tracked files, the environment cleared, and neither the relay socket nor the agent directory mounted. A script there cannot reach the model, the network, the session's process, or the head itself, and every call starts from the unmodified head. The reviewer writes and runs its counterexample there and iterates on it, the way LIBRO and Agentless generate reproduction tests and keep the ones that execution confirms ("Agentless then generates reproduction tests to verify that the issue has been resolved", https://arxiv.org/abs/2407.01489; LIBRO: "rank the produced tests according to their validity", https://arxiv.org/abs/2209.11515).

Dependencies are prepared before, outside both, without running the change's build or install scripts, and passed with `--sandbox-ro` to the scripts and `--ro` to `sandbox.py`. A counterexample that rests on how an external program, service, or library behaves is decided by a fake that returns what the system's official documentation says, or by quoting that documentation; a live external system is not probed, and when neither decides it the cluster stays PLAUSIBLE and its check is not decided. The operator re-runs every reviewer's decisive script itself (`references/consolidate.md` step 3), because a reviewer's account of a run is a claim.

## Procedure

1. Prepare the review directory: the head worktree, `diff.patch` with its sha256, and the requirement copies. Resolve the merge base with `git merge-base` and write the full SHA the command printed, never a hand-copied one: in the first run a mistyped 41-character SHA stopped a reviewer. Plan the units with `python3 -I ~/.agents/skills/rv/bin/plan-units.py --diff diff.patch --repo <head worktree> --out units.json`, and read its summary line (units, files, excluded) before going on; an excluded file is listed with its reason and is not reviewed.
2. Before loading the model server, check that it answers (`curl -sS -m 5 <server>/v1/models`) and whether another session is measuring on it (an open `run-*` terminal of another session that calls it, as the harness instructions require). Launch only when the check succeeded, chaining the launch on its exit code: in the first run a failed check did not stop the launch. When a measurement is running, ask the user whether to launch now and wait for the answer; the answer covers that run only. Asked whether srv should get a standing exception from the harness's measurement check, the user answered (2026-11-15) "앞으로도 확인하고 나한테 물어보도록 해 그럼", which replaced the earlier answer "항상 응답 확인만". Record in the procedure log the server state (for vLLM, `vllm:num_requests_running` and `vllm:num_requests_waiting` from `/metrics`), the user's answer, and how many requests or sessions were launched at what time, so a measurement on that server can account for the load.
3. Design and round 1, chained in one runtime terminal of the operator's workspace (Paseo or Orca, as `~/.agents/skills/agent-runtime/SKILL.md` maps) named `run-srv-<target>-<run number>`, ending the command line with the exit code written to a file, as the harness instructions require for a long run: `uv run ~/.agents/skills/srv/bin/design.py --units units.json --diff diff.patch --repo <head worktree> --requirements <copies> --out design --base-url <server>/v1 --model <model> --api-key-env <variable> && uv run ~/.agents/skills/srv/bin/sweep.py --units units.json --diff diff.patch --repo <head worktree> --design design --requirements <copies> --out round-1 --base-url <server>/v1 --model <model> --api-key-env <variable> [--sandbox-ro <prepared environment>]`. Both need `omp` and `bwrap` on PATH. The change-set session per unit writes `design/<unit>.json`, and the perspective session writes `design/perspectives.json` once the coverage checks pass (section Perspectives); the sweep then starts `--samples` independent reviewer sessions per perspective (default 1), as many at once as the user's thread budget admits (`reviewer.session_slots`: every thread counts against the user's process limit, and on 2026-11-24 39 sessions at once failed to start threads at a limit of 8192, because omp sizes its thread pools to the visible CPUs and ran about 200 threads on 64 of them; each session therefore runs pinned to `reviewer.SESSION_CPUS` CPUs, taken in turn), each with the brief `references/brief.md`, the perspective, the requirement copies, the hunks of its breadth from every unit (`<unit>/H<n>`), their files at the head with line numbers, the lines elsewhere at the head that name a symbol those hunks change, and the file list of the whole change, so the session opens with its tools only what the request lacks. A session's provider errors are retried by omp itself (omp://non-compaction-retry-policy.md); a session that exits non-zero or ends without a final answer uses one attempt. Each answer is validated, retried once when invalid, and its lines are re-located from their anchors; a task is valid only when every sample is, and each task writes `round-1/change__<perspective>.json`; the run writes `summary.json` (with `tool_calls`), `progress.json`, and `sessions.json`, which holds every session's time, usage, and tool calls with their arguments, the `sandbox_run` scripts among them.
4. `design.py` and `sweep.py` exit 1 when a unit has no valid design or a task has no valid output, because that unit, or that perspective of it, is then unreviewed. Read the file's `errors`, remove the cause (endpoint, token limit, schema, an uncovered hunk), and rerun only those with `--only`; the summary then counts every unit or task of the plan again. A failure is never dropped from the review or treated as reviewed, and a design is never written by hand around the coverage check.
5. While the sweep runs, read the designs: a value the change plainly puts at stake that no perspective holds becomes a follow-up question of round 2 (`references/deepen.md`), not an edit of the design.
6. Verify the round by `references/consolidate.md`: take the suggestions from the task files, open every cited `file:line` at the head (the line `anchor-findings.py` re-located; `anchor_status` says how), give each suggestion a verdict, cluster, and re-grade severity; run in the sandbox every suggestion that only a run decides, starting with those of `execute` perspectives. Agreement is not evidence: judge a cluster by the code, never by how many tasks raised it.
7. Write follow-up questions by `references/deepen.md`, including the checks round 1 did not decide by their means and the structural changes whose `high` perspective raised nothing, to `round-<k>/questions.json` (k ≥ 2), and run them in the same kind of terminal: `uv run ~/.agents/skills/srv/bin/followup.py --questions round-<k>/questions.json --units units.json --diff diff.patch --repo <head worktree> --design design --requirements <copies> --out round-<k> --base-url <server>/v1 --model <model> --api-key-env <variable> [--sandbox-ro <prepared environment>]`. Each question gets one reviewer session, with `sandbox_run` when its perspective is `execute`, and answers in round 1's schema. Verify the round as in step 6, merging its suggestions into the existing clusters.
8. Stop when a round adds no new CONFIRMED cluster and every check is decided by its means or recorded as undecided with the reason, or after round 3, whichever comes first.
9. Decide the verdict: write `verdict.json` and run `bin/verdict.py`, as `## Verdict` of `references/consolidate.md` says. The decision is the one it prints.
10. Write the review document `REVIEW.md` in the review directory, in the format of `references/consolidate.md`, and `procedure-log.md` beside it: steps, the design and round-1 `summary.json` numbers, the counterexample runs, sessions per later round with launch and finish times, server state, blockers and what was changed. A time box given to a reviewer is recorded against its actual finish time; it is not a stop, and an overrun is written, not hidden.
11. Remove the head worktree with `git worktree remove` once the review document is written; the review directory keeps every input and output.
12. End the operator's turn with the decision, the counts of confirmed clusters per severity, the residual risks in one line each, the count of new confirmed clusters per round, the precision per round, and the path of `REVIEW.md`, under 4,000 characters. An OUT-OF-SCOPE suggestion reaches the caller only as a count. The caller reads `REVIEW.md`; accepting, rejecting, posting, and fixing are the caller's, and the caller handles the confirmed and PLAUSIBLE clusters as one round of findings with the `response-rv` skill. A criticism of `REVIEW.md` itself (a wrong verdict, a missed cluster, weak evidence) is also handled with `response-rv`, and when its root cause lies in this procedure or its references, fix srv so the same defect does not recur.

The operator edits nothing but the review directory and the head worktree it created: no tracked-file edits, commits, pushes, PR or issue comments, posted reviews, or messages to people. It runs the change's code only inside the sandbox. Reviewer sessions have no tool that writes, sends, or starts sessions. The operator does not stop or restart a model server.

## Limits

This is the goal, not a result; what was reached so far:

Measured on that change (2026-11-24, `deepseek-v4.1-flash` on 100.99.0.1:8000 with no other load, omp 19.1.1, one unit of 11 hunks, recall checked by reading each of the eight findings against the suggestions):

| --- | --- | --- |

End to end that is 646 s against the 540 s target, so the target is not reached. The one-sample run had no false approval (the decision is 차단, as the first review's was) and no false change request (every CONFIRMED BLOCKER or MAJOR cluster is one of the first review's findings); the first review rated one of them BLOCKER that the operator rated MAJOR. Before omp sessions were pinned to four CPUs, each ran about 200 threads and 39 sessions met the user's thread limit; pinned, a session peaked at 35.

Unmeasured: any change but #1470, so neither recall nor the time holds beyond it; the counterexample re-runs of the operator stage; follow-up rounds beyond one smoke question; the level coverage on a change whose structure spans units end to end (on #1726 the change set of the unit holding the record identity marked it structural and an earlier one-step design gave it a `high` perspective, but no full run of #1726 was made). A candidate stage without a threshold remains: every round-1 suggestion goes to the operator, and no reviewer answer carries a score to cut on yet.

Two settings come from the earlier measurement on PR #1415 of the same repository (2026-11-18): two extra samples of a unit found three causes the first missed while an added perspective found none, so a call without tools ran three samples, which the #1470 measurement above replaced for omp sessions with one; and `--max-tokens` counts reasoning tokens, so at 16,384 a quarter of the tasks stopped at the limit and the default is 65,536. A unit shows whole files, smallest first, up to 60,000 characters and the rest as the lines around their changes, because whole manuals made one prompt 166,000 tokens.

Precision is CONFIRMED / (CONFIRMED + REJECTED) per suggestion; it measures how often a suggestion was true, not how many defects the review found. prv's plan trials and the srv runs agree on one point: agreement among reviewers was not evidence.
