# Verify, cluster, and write the review document

## Verify each round

1. Take the suggestions from the `findings` of each task file (`round-1/change__<perspective>.json`, and `round-<k>/change__Q<n>.json` of the follow-up rounds); a reviewer's reported totals are not used. `sessions.json` beside them holds each session's tool calls, the `sandbox_run` scripts among them.
2. Open every cited file:line at the head yourself. For round-1 findings the line is the one `anchor-findings.py` re-located: `exact` and `moved` point at the quoted line, `nearest` at the closest of several equal lines (check that it is the one meant), and `missing` means the quoted text is not at the head, so find the place from the condition or reject the suggestion. Verdict per suggestion: CONFIRMED (you observed the contradiction, omission, or wrong result in the code), PLAUSIBLE (needs execution or more tracing; write the question that would decide it), REJECTED (cite the line that contradicts it), DUPLICATE-OF <cluster>, OUT-OF-SCOPE (outside the change's scope as rv's `## Scope of a finding` in `~/.agents/skills/rv/SKILL.md` defines it; cite the open issue that describes the problem, found with `gh issue list --state open --search "<terms>"`, or the merge-base line that shows it exists the same before the change). An OUT-OF-SCOPE suggestion forms no cluster, gets no severity, and is not verified further.
3. Run what reading cannot decide. A suggestion whose reviewer ran its counterexample with `sandbox_run` carries the script in `sessions.json`: run that script again with `sandbox.py` as below and judge its output yourself, because the reviewer's account of a run is a claim, not evidence. Every other suggestion whose deciding check has the means `execute`, or that only a run decides, gets a counterexample run you write: a small script in the review directory that drives the head's own code with the input or situation the suggestion's condition names (two runs interleaved, a failure injected at a boundary, a fake standing for an external system that returns what that system's documentation says it returns), run with `python3 -I ~/.agents/skills/srv/bin/sandbox.py --repo <head worktree> --out <review dir>/runs/<cluster>-<n> [--ro <prepared environment>] -- <command>`. The sandbox has no network, no caller environment, no home, and no `/run` or `/var`, and works on a copy of the head's tracked files, because the change is untrusted input; prepare its dependencies before, outside it, without running the change's build or install scripts (`uv sync --frozen --no-build`, `npm ci --ignore-scripts`, `cargo fetch`), and mount them with `--ro`, together with the toolchain directories the environment links to (for a uv environment, the uv Python directory). Install only what the run needs when the full dependency list holds a package that ships only as source, and write which ones were left out. When the repository's own test harness refuses to run outside its environment (for example a test configuration that requires its container setup), drive the head's code directly with the script instead of the harness. Keep the script, `run.json`, and the output; the evidence grade of a cluster a run decided is `executed`. When the counterexample rests on how an external program, service, or library behaves and no fake can stand for it, quote the sentence of its official documentation that decides it (evidence grade `documented`); when neither a run nor the documentation decides it, the cluster stays PLAUSIBLE and its check is not decided. The operator never runs the change's code outside the sandbox, and a run is evidence for one verdict, not a test pass: the repository's test suite, CI, real models, and databases stay unrun unless the caller's approval covers them.
4. Verify what you clear as you verify what you confirm. An item listed as checked and cleared, by a reviewer or by you, needs the code path that makes it safe; a reproduction that clears it runs through the same product path the change's users reach (in the first run a cleared item rested on raw sentence splitting without the product's structural post-processing, and the path it cleared was in fact defective).
5. A fix that keeps a current behavior cites the requirement or user decision that asks for it; that the code behaves so is not a ground. In the first run a fix kept the current "nearest heading wins" behavior on no other ground and hid a BLOCKER that a single rv review found.
6. Cluster duplicates across tasks, sessions, and rounds. Agreement among reviewers is not evidence: judge a cluster by the code, not by how many raised it. A duplicate that independently found a confirmed cause counts as CONFIRMED in precision but adds no cluster.
7. Re-grade severity yourself by rv's `## Finding schema` severities; the reviewers' severity is not used.
8. When earlier reviews of the same change are given, mark per cluster whether one already raised it.
9. Per round, per perspective, and per reviewer (a round-1 task counts as one reviewer): suggestions, CONFIRMED, PLAUSIBLE, REJECTED, OUT-OF-SCOPE, and precision = confirmed / (confirmed + rejected). Per round: new CONFIRMED clusters.
10. Per perspective, record whether every check was decided by its means: a `read` check from the code, a `trace` check when the behaviour was followed to its end (in round 1 or by a follow-up question), an `execute` check when its counterexample was run or decided by documentation. A perspective with an undecided check is residual risk, never a pass. For a change with `structure.alters` true, check that a cluster found at `low` depth is not the symptom of a structure: when it is, the cluster names the structure, its fix removes that cause, and its other symptoms join it.

## Verdict

Write `verdict.json` in the review directory: the CONFIRMED and PLAUSIBLE clusters (id, severity, verdict, evidence grade `executed`, `documented`, `traced`, or `read`), the questions only a person can answer (product intent or a specification choice that no record decides, each with the options that meet every existing requirement and what each option changes), every perspective of the design files with `decided` and a note, and the residual risks. Then run `python3 -I ~/.agents/skills/srv/bin/verdict.py --design <review dir>/design --verdict verdict.json --out judgment.json`; it refuses a file that leaves out a designed perspective, and decides by rule: a CONFIRMED BLOCKER or MAJOR is 차단, a PLAUSIBLE BLOCKER or MAJOR or a perspective with an undecided check is 증거 부족, a question or a remaining MINOR or NIT is 조건부 수용, and nothing left is 수용. The review's decision is the one it prints; what was not established never becomes acceptance.

## Review document

Write `REVIEW.md` in Korean, so the caller can read the top section alone and use the rest as it uses an rv review:

1. `## 확정 결함` first: rv's verdict paragraph (the decision `judgment.json` holds, head and merge base as commit links, cluster counts per severity), then a table of every CONFIRMED cluster: id `R-nnn`, severity, head file:line as a link pinned to the head, condition and result, evidence grade with the run directory or the documentation quote, and fix.
2. `## 사람에게 묻는 항목`: the questions of `verdict.json`, each with its options and what each changes.
3. `## 잔여 위험`: the residual risks of `judgment.json`: PLAUSIBLE clusters with the execution or tracing that would decide them, and perspectives with a check not decided by its means.
4. `## 관점`: one row per perspective: id, value, depth (`high` or `low`), the changes of its breadth, whether every check was decided, and its sources.
5. `## 기각한 제안`: each REJECTED suggestion with the line that contradicts it.
6. `## 라운드와 리뷰어 수치`: the numbers of the last step of the verification, with the definition of precision.
7. rv's judgment sections of `## Result format`, filled from the clusters of the perspectives that cover each section; a section no perspective covered says `미확인: 이 관점을 돌리지 않았다` instead of a judgment. Then one section per review area with its findings, `## 확인하고 배제한 항목`, and `## 검증 범위` last, naming the perspectives and rounds run, the scripts run, and what was not run.

Keep the operator's process (sessions, rounds, scripts, blockers) in `procedure-log.md`; `REVIEW.md` carries only what the counts and the verification scope need, so a reader judges the review by its findings.

Read only the reviewer outputs, the inputs they had, the repository, official documentation of the external systems the change relies on, and the repository's open issues (`gh issue list`, `gh issue view`). `REVIEW.md` lists no OUT-OF-SCOPE suggestion; it shows only their count in `## 라운드와 리뷰어 수치`. Edit nothing outside the review directory. No git commits, pushes, PRs, issues, comments or messages.
